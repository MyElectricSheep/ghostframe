# Threat model and frame format

Ghostframe is experimental. Encryption protects the contents of an authenticated frame under the passphrase and cryptographic assumptions. Steganography concerns hiding the existence of a payload. A subtle image change is insufficient evidence of undetectability. The raw-bit command emits unauthenticated guesses and is for research.

## Wire layouts

These layouts are for the legacy frames (`legacy-v1`, `legacy-v2` and the luminance carrier); the current profiles are described in the next paragraph. All offsets start at zero. Each legacy authenticated frame begins with one version byte, a random 16-byte salt and a random 12-byte nonce. Each frame uses a separate fixed profile string and version as associated data. Scrypt derives 32 key bytes with N=131072, r=8, p=1, and a 256 MiB implementation memory ceiling. AES-256-GCM uses a full 16-byte tag. No key is stored in the image.

| Profile | Authenticated plaintext | Ciphertext bytes | Tag bytes | Parity bytes | Total |
|---|---|---:|---:|---:|---:|
| v1 neural | Two-byte big-endian length and 13-byte padded message | 15 | 16 | 0 | 60 |
| v2 neural-ecc | Exactly one message byte | 1 | 16 | 14 | 60 |
| v3 luminance | One-byte length and 26-byte padded message | 27 | 16 | 24 | 96 |

The experimental `ghostframe-png` profiles ([PNG_PROFILES.md](PNG_PROFILES.md)) use a different frame: a random 16-byte salt followed by AES-256-GCM ciphertext and its 16-byte tag. Scrypt with the same parameters derives 44 bytes, split into the key and the 12-byte nonce, so a fresh salt gives a fresh (key, nonce) pair and no nonce is transmitted. There is no version byte. The associated data is the full profile identity (layout, parity, centering, checkpoint digest and calibration digest), so a frame authenticates only under the profile and model that produced it. The plaintext is a one- or two-byte length, the message, and zero padding that the decoder checks. The overhead is 33 or 34 bytes. Interleaved Reed–Solomon blocks surround the frame. The decoder runs scrypt for at most five distinct candidate salts, one from errors-only decoding and one from each of four erasure levels, so its work per image is bounded. Each attempt is an ordinary tag check, and the bound does not change offline guessing cost.

The fixed salt, nonce, tag and version consume 45 bytes before plaintext framing and parity. The v2 one-byte message therefore requires 46 bytes before parity. Reed–Solomon can correct up to seven unknown byte errors in v2 or twelve in v3, or a mix of errors and erasures within the parity budget. Corruption outside the budget is still subject to authentication, which rejects invalid candidates.

## Threat assessment

- **Offline password guesses.** Carrier extraction is public in the authenticated modes, and an adversary can test a passphrase against the tag. Each guess costs one scrypt (N=2^17, r=8, p=1: about 128 MiB and roughly 0.6 s per CPU core). That slows guessing but does not stop it: a weak passphrase still gives weak protection, so use one of several random words. Public benchmark passphrases are for examples.
- **Passphrase bytes.** A passphrase is used as UTF-8 bytes exactly as typed. There is no Unicode normalisation, so the same visible text typed in a different normalisation form will not match, and trailing spaces count. With `--passphrase-file`, the CLI uses the file's bytes as they are, except that trailing newline characters are stripped.
- **No key commitment.** AES-GCM is not key-committing: a ciphertext can in principle be built to authenticate under more than one key. Do not expose decoding as an oracle that tries a stored passphrase on images from others.
- **Detection and known covers.** The previous protocol-aware detector flagged all 14 marked luminance covers and none of their matched clean controls before and after JPEG in the pilot. Someone with an exact clean source can difference the pixels directly. No broad detector resistance or indistinguishability claim follows from the RGB bound. The neural branch has no formal steganalysis assurance. For the `ghostframe-png` profiles, a declared protocol-aware detector that knows the public profile, but not the passphrase, measures how many carrier scores lie near zero. Its result is in [BENCHMARK.md](BENCHMARK.md#detectability). The encoder pushes every score past a margin, so the marked images are statistically distinctive to anyone who runs the public reader. These profiles carry confidential, authenticated messages. They do not hide that a message exists.
- **Fingerprinting.** The public grid, projection schedule, carrier profile, and deterministic model preprocessing can identify the protocol. Wrong-model controls demonstrate rejection on six fixtures across two CPU thread settings. That is a compatibility result, not proof of resistance to identification or attack.
- **Metadata and disclosure.** Passwords and plaintext are never intentionally placed in image metadata. The CLI reserializes image pixels, but this is not a metadata audit or a full anonymization tool. Input and output photos may expose people or locations. Passphrase files, source message files, recovered stdout, shell redirects, and marked-image copies need their own handling.
- **Integrity and availability.** AES-GCM rejects wrong passwords and failed corrections. A modified, resampled, recompressed or removed carrier may be unrecoverable. The decoder needs the expected frame profile and, for neural decoding, the exact checkpoint and preprocessing. Neither frame supplies sender identity, replay protection, or deniability. Anyone who knows the passphrase can create a valid message, so a message that authenticates proves only that its author knew the passphrase. Anyone can destroy a message by editing pixels.
- **Deployment.** The demo site encodes and decodes on a server: the photo, message and passphrase are sent to it over TLS, processed in memory, and dropped when the job ends (see [site/README.md](../site/README.md#privacy)). The host and Cloudflare could see them. Use the command-line tool for anything private.
